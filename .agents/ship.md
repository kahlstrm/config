Ship this thread's change to `main` of kahlstrm/config through a pull request that you merge yourself. No person reviews or approves, so do not ask for confirmation. This prompt authorizes every commit, push to the change's branch, label, PR edit and the merge that the steps below need, in this turn and in the later turns that review and CI messages start, until the PR is merged or you report a stop. Never push to `main`; it takes changes only through PRs.

1. Branch. Commit the uncommitted work that belongs to this change and leave unrelated files alone. If you are on `main`, first create a branch with a short descriptive name; do not ask about a ticket. If the branch's PR is already merged, move the unshipped commits to a new branch from `origin/main`. If nothing differs from `origin/main` and no PR is open, say so and do nothing else.

2. Base. Rebase onto `origin/main` only before the branch's first push, or when GitHub reports the PR as conflicting. Resolve conflicts yourself, and push an already pushed branch with `git push --force-with-lease`.

3. Review. Run the `sol-loop` skill as the root AGENTS.md requires, unless Sol already approved this change's current diff in this thread. After any later change to the branch, sol-loop's "Next round" section decides whether another round is needed, and this prompt extends the budget for those rounds up to sol-loop's limit of 5. A rebase that leaves the change's own diff the same needs no round. If Sol cannot run, or sol-loop ends stuck or out of budget, report that and do not merge.

4. PR. Push the branch. Open a PR against `main` with `gh pr create`, or update the open one: a Conventional Commits title, a description of the change, and sol-loop's result line. If the change is meant to delete a stateful object, lift a protection or change the guard (AGENTS.md, "Destructive changes"), add the label `allow-destroy` and name what is destroyed.

5. Wait. Subscribe to CI for the pushed head commit, then reply with the PR URL and what you are waiting for; do not poll. Each time a CI message arrives, run `gh pr checks <number>` and act on the PR's current head only:
- A check is pending: keep waiting for the next CI message.
- `Destructive change guard` failed: if its log names findings, add `allow-destroy` only if destroying or unprotecting that is what this change is for; otherwise fix the change. If it failed before checking (checkout, setup or fetch) or was cancelled, rerun it with `gh run rerun <run-id>` and wait again. The guard is never counted as passed without a successful run.
- Another check failed because of this change: fix it, push, and wait again.
- Another check failed or was cancelled for a reason outside this change: rerun it once with `gh run rerun <run-id> --failed`. If it fails again and the same job also fails in that workflow's latest run on `main`, count it as passed and name the check and that run in the PR description. Otherwise treat it as caused by this change.
- Actions cannot run at all: do the local checks from AGENTS.md ("When remote CI cannot run") and record them in the PR. The merge still waits for the guard, so report that the PR waits for Actions. When you are told to ship again and the head has no guard result, close and reopen the PR to start the checks.

6. Merge. When the guard has passed on the head commit, every other check has passed, been skipped or been counted as passed above, and Sol's approval covers that commit, run `gh pr merge <number> --squash --match-head-commit <sha>`. Do not use `--auto` or `--admin`. If GitHub refuses the merge, fix the cause it names (step 2 for a conflict) instead of working around it. Confirm with `gh pr view <number> --json state,mergeCommit`, then report the PR URL, the merge commit and any rollout the PR's description still calls for.
