# Keep every secret as sops files in one private repository

- Status: accepted, migrating (nothing moved yet)
- Date: 2026-11-11
- Supersedes: [the secret-edits ADR](2026-11-10-secret-edits-on-the-ops-runner.md)
- Amends: [the frictionless shipping ADR](2026-11-10-agents-ship-without-approvals.md)
  and [the ops retirement ADR](2026-11-10-retire-the-ops-vm.md), on `just edit`,
  Secret Manager and the appliers' credentials;
  [the runners ADR](2026-11-09-amp-runners-on-hosts.md) and
  [the declarative state ADR](2026-11-09-keep-agent-state-declarative.md), on
  runner tokens in systemd credentials;
  [the runner model ADR](2026-11-09-one-runner-per-managed-thing.md), on
  Secret Manager for orbs and the klusse runner's key

## Context

Secrets live in five places: SOPS files in this public repository for the
cluster, agenix files for hosts, Google Secret Manager for provider tokens
(synced into the cluster by External Secrets and read by Terraform), systemd
credentials placed by hand for runner tokens, and Terraform state.

Each place has its own way to add a value. Most need a maintainer at a
terminal. The public ciphertext and its history are readable by anyone who
later holds one recipient key, and one daily-use administrator SSH key is a
recipient of almost every file. Two of those files hold credentials usable from
the internet: the agents' GitHub App key and the Headscale OIDC client secret.

## Decision

- **One private repository, `kahlstrm/secrets`, holds every secret as a sops
  file**: cluster secrets, host secrets, provider tokens, and the inputs of the
  Terraform layers. It replaces Secret Manager, External Secrets, agenix,
  systemd credentials for runner tokens, and `just edit`. Terraform reads its
  inputs through the sops provider. The Terraform state bucket stays.
- **Each file is encrypted only to its consumers plus one offline recovery
  key.** Consumers are a host's SSH host key, the Flux age key, or a Terraform
  layer applier's own age key. No daily-use administrator key is a recipient.
  The recovery key's private half is kept offline only.
- **One value per file.** Agents add or rotate a value by encrypting a new file
  with public keys only. They never decrypt and hold no credential. A value a
  machine can generate is generated by the agent and never printed. A value only
  a person has is entered once through Amp's masked secret prompt and the
  temporary Amp secret is deleted after it is encrypted.
- **The offline store holds three values only:** the recovery key, the backup
  repository password and the backup storage key. Everything else that must
  survive the loss of its system, such as the Flux age key and the Talos machine
  secrets, has a copy in the private repository encrypted to the recovery key
  alone.
- **Readers:**
  - Hosts read the repository as a flake input (`inputs.secrets`,
    `flake = false`), so ciphertext reaches hosts and their VMs through the Nix
    store and only the machine that evaluates a configuration fetches it. Hosts
    that evaluate their own configuration use their SSH host key as a read-only
    deploy key. CI uses a read-only deploy key of its own.
  - Flux reads it as a second `GitRepository` with a deploy key generated in the
    cluster.
  - Terraform layer appliers read it from the revision pinned in `flake.lock`.
- **Migration order:** the recovery key replaces the administrator keys as
  recipient first, then the GitHub App key and the Headscale OIDC secret are
  rotated into the private repository. The remaining layers (cluster, Terraform,
  hosts) move only once off-host backups run. Every move copies the value,
  switches the reader, verifies it, and only then removes the old copy.

## Flux's keys

Flux needs two secrets before it can read anything: the age key it decrypts
with, and the deploy key for the private repository. Both become Talos inline
manifests rendered by `local-talos`, the same way the `FluxInstance` is
created today (`local-talos/flux.tf`). Their source files in the private
repository are encrypted to the `local-talos` applier's key and the recovery
key. A rebuilt cluster then comes up able to decrypt, with no manual step.

The values end up in the `local-talos` state and the control planes' machine
configuration. Both already hold the Talos machine secrets, which grant
cluster-admin and so the Secrets themselves, so no new reader gains access.

The switch keeps the same age key under a new Secret name. The Flux
Kustomizations' `decryption.secretRef` moves to it, decryption is verified, and
only then is the `sops-age` ExternalSecret removed. Until `local-talos` reads
sops, the private repository's deploy key is created once in the cluster with
`flux create secret git`.

## Secret Manager and the Terraform state

- **Terraform state stays in the existing GCS bucket**, versioned and
  protected from deletion. The GCP project keeps only the state bucket and the
  appliers' service accounts. Moving the state elsewhere would add a credential
  and a migration and remove no risk: the state holds the Talos machine secrets
  wherever it lives.
- **Provider credentials stay out of the state.** Layers read them with the
  sops provider's ephemeral `sops_file` (Terraform 1.11 or later, provider
  `carlpett/sops` 1.3 or later) in provider blocks and write-only arguments.
  Values Terraform writes into a target, such as router user passwords and the
  Talos inline manifests, are stored in the state as today, so read access to
  the state stays equivalent to admin.
- **Secret Manager is removed once every reader has moved and been verified:**
  External Secrets and its workload identity provider, the `local-kubernetes`,
  `local-networking` and `hetzner-infra` secrets, their IAM grants, the `just`
  recipes that edit them, `infra/modules/secrets`, and finally the
  `secretmanager.googleapis.com` service in `gcp-project`. Each secret is
  deleted by a declared destroy, after its values are in the private repository
  and a backup restore check has passed.

## What this changes in earlier decisions

- **[The frictionless shipping ADR](2026-11-10-agents-ship-without-approvals.md)**
  lists `just edit` as a recurring human step to automate or drop. It is
  dropped: a value only a person has is entered once through the masked
  prompt, and every other value is generated by an agent. Losing the Google
  account now loses the Terraform state only. The Flux age key and the Talos
  machine secrets keep a copy in the private repository, encrypted to the
  recovery key.
- **[The ops retirement ADR](2026-11-10-retire-the-ops-vm.md)** sends Secret
  Manager edits to orbs, with `just edit` until then. Orbs now write sops
  files instead. Each applier gets an age key of its own, readable only by its
  user, and reads its credentials from the private repository. Its Secret
  Manager read grant is removed with Secret Manager.
- **The secret-edits ADR** kept `local-kubernetes` as one Secret Manager
  document because Secret Manager bills per version, and left its edits to
  `just edit`. Secret Manager is removed, so neither holds. Its GCP grants stay
  unapplied.
- **Runner tokens** stay in `/etc/credstore.encrypted` until their host's
  layer moves. Then each is a file encrypted to its host key and the recovery
  key, rotated by PR. The klusse runner's key moves with the cluster's secrets.
- **Converting agenix to sops-nix** happens as part of this move, with the files
  in the private repository instead of this one.
- **New secrets go to the private repository** once their layer reads from
  it. Until then they follow the existing rules and move with the layer. The
  ops VM's host-only sops rule is not used again.

## Consequences

- Secret names, recipients and change history are no longer public, and a
  leaked recipient key is not enough without read access to the repository.
  The exception is the host key of a host that evaluates its own configuration:
  it is also that host's deploy key, so its theft gives both.
- Values committed here before stay readable with the keys they were encrypted
  to. Re-encrypting them protects nothing, so each value that matters is
  rotated when it moves, unless its target can't accept a new value.
- Agents working in this repository can't read secrets, as before. Changing a
  host secret takes two merges: the file in the private repository, then a
  `flake.lock` update here. Flux follows the private repository directly.
- Two credentials are new: the Flux deploy key and the CI deploy key. Both read
  ciphertext only.
- Losing the recovery key loses every root copy; losing a consumer key loses
  only that consumer's files, which the recovery key re-encrypts.
